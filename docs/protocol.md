# Streamweld durable-stream protocol

Status: normative for protocol version 1

Last updated: 2026-08-22

This document is the implementation contract for Streamweld's data plane, journal
backends, CLI, operator, and client SDKs. The words **MUST**, **MUST NOT**,
**SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described by
RFC 2119.

Streamweld extends the OpenAI streaming APIs with a durable stream identity and
an ordered, append-only journal. It does not change model inference, scheduling,
or token generation. A generation is owned by its `stream_id` rather than by
one downstream HTTP connection.

## 1. Protocol invariants

Every conforming implementation preserves these invariants:

1. A streaming generation has exactly one lowercase ULID `stream_id`.
2. The journal sequence begins with an `open` entry at `seq=1`, increases by
   one for every entry, and never reuses a sequence number.
3. A `done`, `error`, or `stopped` entry is terminal. No entry may be appended
   after it.
4. An acknowledged journal entry is durable according to the selected journal
   backend before it is made available for replay.
5. A resume cursor is exclusive: `Last-Event-ID: N` requests entries whose
   sequence is greater than `N`.
6. Replay followed by live tailing has no gap and no duplicate at the
   read-to-tail boundary.
7. A downstream disconnect does not mean stop. Only the stop endpoint is a
   user-initiated stop.
8. A producer never waits for a slow downstream reader. Journal writes follow
   producer progress; every reader has independent backpressure.
9. Streamweld emits only complete upstream SSE events and complete UTF-8
   sequences. It never journals a partial SSE event or a split UTF-8 rune.
10. Producer migration is attempted only after all policy and correctness gates
    pass. A refused migration is represented by a warning followed by a
    terminal error.
11. A journal outage never rejects an otherwise serviceable inference request.
    The request continues in explicitly degraded pass-through mode.

## 2. Terms and state model

- **Producer**: the upstream OpenAI-compatible inference backend currently
  generating a stream.
- **Reader**: one downstream HTTP connection consuming the initial stream or a
  resumed stream.
- **Origin backend**: the backend selected for the first generation attempt.
- **Attempt**: one upstream request, including the origin request and each
  continuation request.
- **Accumulated text**: assistant text already accepted into the journal after
  UTF-8 validation and seam reconciliation.
- **Journal cursor**: the greatest journal `seq` a reader has processed.
- **Resumable**: journal entries remain available and the stream was not
  explicitly stopped.
- **Terminal**: the journal contains `done`, `error`, or `stopped`.

A stream has this state machine:

```text
               +---------------- migration ----------------+
               |                                           |
created -> open/producing ----------------------------------+
                  |            |                    |
                  |            |                    |
                 done         error               stopped
```

All three terminal states are final. Migration is an event within
`open/producing`, not a separate durable state.

## 3. Common representation

### 3.1 Stream identifiers

A `stream_id` MUST be a canonical 26-character ULID:

- generated by Streamweld before opening the upstream streaming response;
- encoded with lowercase Crockford Base32;
- lexically sortable by creation time;
- generated with sufficient entropy to avoid collisions across proxy replicas;
- accepted in API paths only in canonical lowercase form.

The server MUST reject a non-canonical identifier with `400 Bad Request` rather
than normalizing it. A collision during journal `Open` causes the server to
generate a new ID; it MUST NOT attach a new request to a collided ID.

### 3.2 Time, counters, and JSON

- `ts` values use UTC RFC 3339 with fractional seconds, for example
  `2026-08-22T10:15:03.221Z`.
- `seq` is an unsigned 64-bit integer represented as a JSON integer and as an
  unsigned decimal string in SSE `id:` fields.
- Token and byte counts are non-negative JSON integers.
- Protocol JSON is UTF-8. Unknown object members MUST be ignored by readers so
  fields can be added compatibly.
- Error and event `code` values are stable machine-readable lowercase
  snake-case strings. Human-readable `message` values are not stable API keys.

### 3.3 Request headers

| Header | Applies to | Meaning |
|---|---|---|
| `X-Streamweld-Idempotency-Key` | initial streaming POST | Reuse an existing stream identity within its journal lifetime |
| `X-Streamweld-Verbose: 1` | initial or resume request | Include `migration` and `warning` journal entries |
| `X-Streamweld-Orphan-Policy` | initial streaming POST | Per-request override: `continue`, `cancel_after`, or `cancel` |
| `Last-Event-ID` | resume GET | Exclusive decimal journal cursor |

Header names are case-insensitive. Header values are interpreted exactly as
specified; unsupported values receive `400 Bad Request` before a stream opens.

Every durable initial streaming response, including an idempotent replay, MUST
include:

```http
X-Streamweld-Stream-Id: 01k3...
X-Streamweld-Durability: durable
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-store
```

When the configured journal cannot open a stream, the request is served in
pass-through mode and the response instead includes
`X-Streamweld-Durability: degraded`. This response has no resumable identity;
`X-Streamweld-Stream-Id` MUST be omitted. The degraded gauge and a structured
log record MUST also be emitted.

## 4. Initial request lifecycle

### 4.1 Streaming chat completions

`POST /v1/chat/completions` with `"stream": true` follows this order:

1. Validate routing, headers, request size, and JSON. Failures before journal
   creation use an ordinary OpenAI-shaped HTTP error and create no stream.
2. Canonicalize the request once while preserving unknown JSON members. Store
   this normalized request in private stream state for possible continuation.
3. Resolve the route policy and a valid per-request orphan-policy override.
4. Resolve an idempotency key, if supplied, as described in section 9.
5. For a new key/request, select a healthy, non-draining backend, resolve its
   model version, and reserve it for the first attempt. An idempotent hit skips
   selection and attaches to the existing stream.
6. Allocate a `stream_id` and atomically create the idempotency mapping and
   `open` journal entry using the selected backend metadata.
7. Dispatch the normalized request to the reserved backend and wait for its
   response headers. A connection failure or `5xx` is a migration trigger under
   section 11, even when it happens before a downstream response is committed.
8. On a successful streaming response, return `200 OK`, the stream ID header,
   and an SSE body. The first SSE event is the `open` entry.
9. Parse complete upstream SSE events, append each accepted event to the
   journal, and independently publish it to all attached readers.

Once the `open` entry exists, producer failures are represented in the SSE
journal. They do not change the already-sent HTTP status.

An upstream `4xx`, including `429`, is a request rejection rather than a
producer-failure signal in protocol v1. Streamweld appends and closes with an
`error` entry whose reason is `upstream_rejected`, returns the upstream status
and OpenAI-shaped error body, and includes `X-Streamweld-Stream-Id`. Because the
response is not successful SSE, it has no first `open` event; the complete
journal remains queryable by ID. The proxy MUST bound and sanitize any upstream
error text before placing it in the client-visible journal. It MUST NOT retry or
migrate a rejected request automatically.

The request body stored for continuation MUST exclude proxy-only headers and
transport state, MUST retain all unknown backend-specific JSON fields, and MUST
not store authorization credentials in a client-visible journal entry.

### 4.2 Legacy completions

`POST /v1/completions` supports streaming journal, resume, stop, and orphan
semantics. Producer migration in protocol v1 is safe only for a single textual
choice (`n` absent or `n=1`) with one string prompt. For that shape,
Streamweld appends accumulated output to the original prompt and applies the
same remaining-token and seam rules as chat continuation.

Array prompts, multiple choices, and non-text deltas remain resumable across
consumer disconnects but are migration-ineligible. On a producer failure they
receive warning code `unsupported_continuation_shape` followed by terminal
error code `migration_refused`. They are never silently restarted.

### 4.3 Non-streaming requests

`POST /v1/chat/completions` and `POST /v1/completions` with `"stream": false`
or no `stream` member are direct OpenAI-compatible pass-through requests.
Journaling, stream ID creation, idempotency mapping, resume, stop, and migration
are disabled. Streamweld MUST stream neither the request nor response through a
journal buffer and adds no durability-related round trip.

## 5. Journal contract

### 5.1 Interface

Go implementations expose this interface:

```go
type Journal interface {
    Open(ctx context.Context, id StreamID, meta Meta) error
    Append(ctx context.Context, id StreamID, e Entry) (seq uint64, err error)
    Read(ctx context.Context, id StreamID, fromSeq uint64) (iter.Seq2[Entry, error], error)
    Tail(ctx context.Context, id StreamID, fromSeq uint64) (<-chan Entry, func(), error)
    State(ctx context.Context, id StreamID) (StreamState, error)
    Close(ctx context.Context, id StreamID, terminal Entry) error
}
```

The interface has these observable semantics:

- `Open` creates the stream and atomically appends `open` as sequence 1.
  Existing IDs fail with an already-exists error.
- `Append` rejects `open` and terminal kinds. It atomically allocates the next
  sequence and returns only after the entry is committed.
- `Read(id, N)` yields committed entries with `seq > N` in increasing order,
  then ends at the snapshot boundary. Iterator errors are surfaced as values.
- `Tail(id, N)` yields committed entries with `seq > N` and then waits for new
  entries. It closes after a terminal entry. The cancel function is idempotent,
  releases backend resources, and causes the channel to close.
- `State` returns metadata, current sequence bounds, status, usage, resumability,
  and migration history without consuming entries.
- `Close` accepts exactly one terminal entry and atomically appends it while
  marking the stream closed. Concurrent closes have one winner; subsequent
  closes return the existing terminal-state error and append nothing.
- Concurrent appends for one stream are serialized. A successful caller can
  rely on its returned `seq` as the committed order.
- Implementations MUST prevent the replay/tail race. Entries committed between
  a snapshot read and a blocking tail subscription must still be delivered.

### 5.2 Entry envelope

Every stored entry has this envelope:

```json
{
  "seq": 42,
  "ts": "2026-08-22T10:15:03.221Z",
  "kind": "chunk",
  "payload": {}
}
```

`seq` is assigned by the journal, not by callers. `ts` records acceptance into
the journal. `payload` is always a JSON object and follows the kind-specific
contracts below.

### 5.3 Entry kinds and payloads

#### `open`

```json
{
  "stream_id": "01k3...",
  "model": "meta-llama/Llama-3.1-8B-Instruct",
  "model_version": "sha256:...",
  "backend_id": "backend-7"
}
```

`model_version` MAY be null when the backend cannot report a version. An
unknown version makes cross-backend migration ineligible unless
`allow_cross_version` is true. `backend_id` is an operator-assigned opaque ID,
not necessarily a network address.

#### `chunk`

```json
{
  "data": "{\"choices\":[{\"delta\":{\"content\":\"hello\"}}]}",
  "upstream_event": null
}
```

`data` is the upstream SSE data payload after standards-compliant SSE decoding:
multiple `data:` lines are joined with a single LF. It is stored as a string,
even when it contains JSON. Except for seam removal on a continuation attempt,
the payload bytes are unchanged. `upstream_event` records a non-empty upstream
`event:` value for diagnostics; downstream chunk delivery does not reuse that
event name.

The upstream `[DONE]` marker is not a `chunk`. It closes the stream with a
`done` entry.

#### `migration`

```json
{
  "from_backend": "backend-7",
  "to_backend": "backend-9",
  "reason": "tcp_reset",
  "rescued_tokens": 317,
  "token_count_estimated": false,
  "attempt": 2
}
```

Allowed reason codes are `tcp_reset`, `unexpected_eof`, `error_chunk`,
`upstream_5xx`, `health`, `drain`, and `stall`. `attempt` is one for the
origin request and increases for every continuation, so the first migration
has `attempt: 2`. The entry is committed before any accepted continuation
chunk.

#### `warning`

```json
{
  "code": "eligibility_failed",
  "message": "migration token limit reached",
  "predicate": "max_migration_tokens",
  "details": {}
}
```

`predicate` and `details` MAY be null. Standard warning codes are:

- `eligibility_failed`;
- `seam_anomaly`;
- `template_degraded`;
- `template_unsafe_permissive`;
- `structured_prefix_invalid`;
- `tool_call_boundary`;
- `unsupported_continuation_shape`;
- `token_count_estimated`.

Warnings do not close the journal.

#### `error`

```json
{
  "code": "migration_refused",
  "message": "continuation is not safe",
  "reason": "tool_call_boundary",
  "retriable": false,
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 317,
    "total_tokens": 445,
    "estimated": false
  }
}
```

An `error` is terminal for this stream. `retriable` describes retrying this
stream identity and is therefore always false in protocol v1; a caller may
choose to start a separate generation. Standard error codes include
`upstream_error`, `migration_refused`, `migration_exhausted`,
`orphan_cancelled`, `journal_capacity_exceeded`, and
`proxy_shutdown_timeout`.

#### `done`

```json
{
  "finish_reason": "stop",
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 512,
    "total_tokens": 640,
    "estimated": false
  }
}
```

The final upstream finish reason MAY be null. Usage totals MUST be present. If
the backend did not provide complete accounting, Streamweld supplies its best
conservative count and sets `estimated: true`.

#### `stopped`

```json
{
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 91,
    "total_tokens": 219,
    "estimated": true
  }
}
```

`stopped` is used only for an explicit stop request. The partial text is
returned by the stop endpoint and can also be reconstructed from retained chunk
entries; it is not duplicated in the terminal journal payload.

### 5.4 Retention and capacity

Active streams MUST NOT expire because their creation time exceeds the journal
TTL. Their expiry is refreshed as entries are committed. A terminal stream is
retained for `journal.ttl` after its terminal commit; the default is `10m`.
The idempotency mapping has the same lifetime as the stream.

Backends retain a compact existence tombstone for one additional
`journal.ttl` after event data expires. This makes `stream_expired`
distinguishable from `stream_not_found` without retaining generated text.
After the tombstone itself expires, the ID is indistinguishable from an ID that
never existed and is reported as `stream_not_found`.

The memory backend maintains a bounded ring per stream and enforces
`journal.max_bytes_per_stream`, default `4MiB`. If old entries must be removed,
it records `earliest_seq`. A resume cursor older than that boundary receives
`stream_offset_expired`; the implementation MUST NOT return a silently
truncated replay.

`journal.max_total_bytes` is a hard global cap in memory mode. The backend
evicts least-recently-used terminal streams first and never evicts an active
stream merely to admit another active append. If terminal eviction cannot make
space, the affected generation transitions to degraded pass-through behavior;
the current reader continues, but durability is no longer promised. This
condition is surfaced through the degraded metric, a structured log, and a
non-journaled `streamweld.stream.warning` control event.

The Redis backend stores journal entries in Redis Streams and implements append,
range replay, and blocking tail with `XADD`, `XRANGE`, and `XREAD BLOCK`.
State changes, sequence assignment, idempotency mapping, and terminal closure
must be atomic. Stream keys receive the per-stream TTL only after termination
or while refreshed by active writes. The producer's normal path performs the
append needed for durability but no read or tail round trip when no reader is
resuming; the initial attached reader may be fed from the producer after commit.

Memory mode is single-proxy-replica only. Its journals and idempotency bindings
are process-local and do not survive process exit. Cross-replica replay and
proxy failover require Redis.

## 6. Downstream SSE representation

### 6.1 Journal-entry mapping

Each visible journal entry is emitted as one complete SSE event. Its `id:` is
the journal sequence. Visibility and encoding are:

| Journal kind | SSE `event:` | SSE `data:` | Default visibility |
|---|---|---|---|
| `open` | `streamweld.stream.open` | JSON payload | visible |
| `chunk` | omitted (default message event) | exact `payload.data` string | visible |
| `migration` | `streamweld.stream.migration` | JSON payload | verbose only |
| `warning` | `streamweld.stream.warning` | JSON payload | verbose only |
| `error` | `streamweld.stream.error` | JSON payload | visible, then close |
| `done` | `streamweld.stream.done` | JSON payload | visible, then `[DONE]` and close |
| `stopped` | `streamweld.stream.stopped` | JSON payload | visible, then close |

The `open` payload on the wire includes `stream_id` and is the first SSE event
on every initial stream or full replay from sequence zero. A chunk omits
`event:` so ordinary OpenAI SSE consumers continue to receive message events.
If chunk data contains LF characters, each logical line is serialized as its
own `data:` field as required by SSE; decoding recreates the journaled string.

After a visible `done` event, the server emits the OpenAI compatibility sentinel
`data: [DONE]` as an unsequenced transport event and closes. The sentinel is not
journaled. A terminal-success resume whose cursor already equals the terminal
sequence still receives the sentinel before close.

Filtering a non-verbose `migration` or `warning` does not renumber entries.
Visible SSE IDs may therefore have gaps. Those gaps are intentional and the
next visible ID advances the reader cursor past the hidden entries.

### 6.2 Upstream SSE parsing

The proxy uses an incremental SSE parser, not line-oriented JSON scanning:

- CRLF, LF, and CR line endings are accepted.
- Multiple `data:` lines form one payload joined by LF.
- A blank line dispatches one event.
- Comment lines are recognized. They MAY be forwarded live as unsequenced
  heartbeat comments but are not journaled.
- `retry:` is parsed and validated but is not allowed to alter Streamweld's
  client resume policy.
- Upstream `id:` values are not forwarded because journal `seq` is the
  downstream event ID.
- A final unterminated event at clean EOF is dispatched only if the SSE grammar
  defines it as complete. EOF without an upstream terminal marker remains a
  producer-failure trigger.
- A UTF-8 byte sequence split across socket reads is buffered until complete.
  Invalid UTF-8 is a producer error; its bytes are never journaled as text.
- A frame whose non-delimiter wire content exceeds `sse.max_event_bytes` is a
  producer error with reason `sse_event_too_large`. The default is 1MiB and the
  bound applies to recognized fields, comments, and unknown fields alike.

One upstream SSE event yields at most one chunk entry. Buffering and seam
rewriting may delay it, but the proxy never exposes half an SSE event.

### 6.3 Reader backpressure

Every reader has a bounded outbound queue governed by
`reader.max_lag_bytes`. Publishing to one queue MUST NOT block journal append or
another reader. When a reader exceeds the limit, the proxy sends an unsequenced
`streamweld.reader.error` event with code `reader_lag_exceeded` when the socket
is still writable, then closes only that reader. The stream and producer remain
active, subject to orphan policy after the final reader detaches.

Each downstream stream write and flush is bounded by
`reader.write_timeout`, default `30s`. When the deadline expires, the proxy
closes only that reader and detaches it from the stream; producer progress and
other readers remain unaffected.

SSE heartbeat comments MAY be sent to keep intermediaries from considering an
idle stream dead. Heartbeats are never journaled and never advance
`Last-Event-ID`.

## 7. Resume and fan-out

### 7.1 Endpoint

```http
GET /v1/streams/{stream_id}/events HTTP/1.1
Last-Event-ID: 41
Accept: text/event-stream
```

An absent `Last-Event-ID` means zero. A present value MUST be a canonical
unsigned decimal integer. Negative, signed, whitespace-padded, overflowing, or
otherwise malformed cursors receive `400 invalid_resume_cursor`. A cursor
greater than the journal's `last_seq` receives `409 cursor_ahead`.

For a valid cursor the proxy:

1. validates existence, retention, and resumability;
2. responds `200 OK` with `text/event-stream`;
3. replays retained entries with `seq > cursor`, applying verbose filtering;
4. atomically continues with live entries after the replay boundary;
5. closes after the terminal entry, or immediately after replay if already
   terminal.

If a done cursor already equals the terminal sequence, the response contains
only the unsequenced `[DONE]` sentinel and closes. If an error or stopped cursor
equals its terminal sequence, the response has no events and closes.

Any number of readers may attach concurrently. A second reader from sequence
zero receives the complete retained journal and then the same live tail. Reader
attachment and detachment do not transfer producer ownership.

In Redis mode a non-owner proxy MAY establish a private streaming relay to the
producer owner before committing the public response headers. This relay is
needed only to carry live data which may become unjournaled after a Redis
failure; Redis remains authoritative for committed replay. The owner identity
and relay URL are private journal metadata and MUST NOT appear in the open event
or public stream-state response. An events relay request MUST forward only the
stream identity, cursor, and verbose selection. A stop relay request MUST
forward only the stream identity and stop operation, with an empty body. Relay
responses MUST expose only the allowlisted public streaming or stop-response
headers. Client authorization, cookies, idempotency keys, arbitrary headers,
and public request bodies MUST NOT cross the internal hop.

A production relay MUST use a separate private listener, TLS 1.3, and mutually
verified certificates. Plain HTTP is permitted only in an explicitly enabled
development mode whose listen and advertised endpoints are both loopback. An
advertised URL MUST route directly to one replica; a load-balanced address does
not preserve owner routing. Owner presence is leased through Redis so a new
reader does not route to a stale process. Failure to establish the relay before
public headers are committed falls back to the Redis tail.

### 7.2 Resume failures

All protocol errors use:

```json
{
  "error": {
    "type": "streamweld_error",
    "code": "stream_expired",
    "message": "stream journal has expired",
    "stream_id": "01k3..."
  }
}
```

| Condition | HTTP status | `code` |
|---|---:|---|
| ID has an expiry tombstone but no journal | 410 | `stream_expired` |
| ID and tombstone were never observed | 410 | `stream_not_found` |
| Requested cursor precedes retained ring data | 410 | `stream_offset_expired` |
| Stream was explicitly stopped | 410 | `stream_not_resumable` |
| Cursor is malformed | 400 | `invalid_resume_cursor` |
| Cursor is greater than `last_seq` | 409 | `cursor_ahead` |

A client MUST surface a 410 as expiration/non-resumability and MUST NOT issue a
new generation automatically. In particular, `@streamweld/client` maps these
responses to `StreamExpiredError` with the server `code`.

## 8. Stream state

`GET /v1/streams/{stream_id}` returns `200 OK` and:

```json
{
  "stream_id": "01k3...",
  "status": "open",
  "resumable": true,
  "model": "meta-llama/Llama-3.1-8B-Instruct",
  "model_version": "sha256:...",
  "origin_backend": "backend-7",
  "current_backend": "backend-9",
  "created_at": "2026-08-22T10:15:03.221Z",
  "updated_at": "2026-08-22T10:15:09.002Z",
  "earliest_seq": 1,
  "last_seq": 47,
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 317,
    "total_tokens": 445,
    "estimated": false
  },
  "migrations": [
    {
      "seq": 42,
      "from_backend": "backend-7",
      "to_backend": "backend-9",
      "reason": "tcp_reset",
      "rescued_tokens": 317,
      "attempt": 2
    }
  ],
  "terminal": null
}
```

`status` is `open`, `done`, `error`, or `stopped`. `terminal` is null while
open and otherwise contains the terminal entry payload and sequence. This
endpoint does not return the prompt, credentials, or accumulated output text.
Unknown and expired IDs use the same 410 distinctions as the events endpoint.

## 9. Idempotency

`X-Streamweld-Idempotency-Key` is an opaque, non-empty client value scoped to
the configured journal namespace. The proxy stores only a collision-resistant
digest of the value. Resolution and stream creation MUST be atomic across
replicas.

- The first key use creates one stream.
- A later streaming POST with the same key while the mapping is retained MUST
  return that existing stream and MUST NOT contact a backend for a new
  generation.
- The later request body and model do not replace the original normalized
  request. The original stream is authoritative.
- If the stream is active, the duplicate request replays from sequence zero and
  tails live.
- If it ended in `done` or `error`, the duplicate request replays through the
  terminal entry and closes.
- If it ended in `stopped`, the duplicate returns `410
  stream_not_resumable` and includes `X-Streamweld-Stream-Id`. It still does
  not start a replacement generation.
- After the mapping expires, the key is new and may create a new stream.

Idempotency applies only to durable streaming POSTs. The value is never sent to
an inference backend or exposed in journal/state responses.

## 10. Stop and consumer disconnect

### 10.1 Explicit stop

`POST /v1/streams/{id}/stop` is the sole user-stop operation. On the first
valid call the proxy:

1. marks the stop requested so no migration can begin;
2. cancels the current upstream attempt;
3. commits a terminal `stopped` entry;
4. marks the journal non-resumable;
5. notifies attached readers with the `stopped` event and closes them.

The response is `202 Accepted`:

```json
{
  "stream_id": "01k3...",
  "outcome": "stopped",
  "partial_text": "The response generated before stop",
  "usage": {
    "prompt_tokens": 128,
    "completion_tokens": 91,
    "total_tokens": 219,
    "estimated": true
  }
}
```

In Redis mode, a relay-enabled non-owner proxy resolves the live owner and
forwards an empty internal stop request over the same mutually authenticated
private listener used for event relay. It MUST NOT forward the public request
body or headers. If the relay is unavailable while shared state remains
readable, the non-owner surfaces `stream_owner_unavailable`; if Redis is also
unavailable, it surfaces `journal_unavailable`. It MUST NOT synthesize a stopped
entry without canceling the owning producer.

Repeated stop calls on an already-stopped stream are idempotent and return the
same logical result with `202`. A stop racing with `done` or `error` returns
`409 stream_already_terminal` and does not replace the winning terminal entry.
Unknown or expired IDs return the section 7.2 response. The stop response is
not sent until the terminal state is committed, even though its status is 202.
The stopped terminal payload retains `partial_text` and `usage`, allowing the
same response to be reconstructed after owner loss or a proxy restart.

An `AbortSignal` or socket close affects only that reader. It MUST NOT be
translated into this endpoint.

### 10.2 Orphan policy

The effective policy is the route's policy unless a valid
`X-Streamweld-Orphan-Policy` overrides it:

- `continue` (default): zero readers has no effect on the producer.
- `cancel_after`: when the last reader detaches, start the configured
  `orphan_timeout`, default `60s`. Attaching any reader before expiry cancels
  the timer. If it expires while the reader count is still zero, cancel the
  producer and close with `error` code `orphan_cancelled`.
- `cancel`: when the last reader detaches, immediately cancel the producer and
  close with `error` code `orphan_cancelled`.

Reader count includes the initial POST connection and every resume/fan-out
connection. A transport replacement is allowed to briefly reduce the count to
zero; only `cancel_after` provides a reconnection grace period. Orphan
cancellation is not user-initiated and therefore never writes `stopped`.

## 11. Producer failure and migration

### 11.1 Detection

The following conditions trigger evaluation in descending order of confidence:

1. upstream TCP reset or EOF without `[DONE]` or another valid terminal signal;
2. an upstream error object/event inside the stream;
3. upstream HTTP 5xx before or during the stream;
4. health-check failure for the backend bound to the stream;
5. the backend enters draining state;
6. an inter-token stall exceeds `migration.stall_timeout`.

The default stall timeout is `30s`, but stall detection is disabled by default
and must be explicitly enabled because slow generation can otherwise look like
failure. When more than one detector observes the same failed attempt, the
first detector to atomically transition the attempt into failing owns
migration; the others append nothing.

Detection reason maps to metrics as follows: TCP reset, unexpected EOF, and
upstream 5xx use `reason="crash"`; the other reasons use `error_chunk`,
`health`, `drain`, or `stall`.

### 11.2 Eligibility

All predicates are evaluated from one state snapshot:

```text
migrations_used        < policy.max_migrations
accumulated_tokens     < policy.max_migration_tokens
elapsed                < policy.max_stream_duration
template policy permits template_verdict(model)
response_format is text OR policy.allow_structured_resume
(origin and target model versions are known and equal) OR policy.allow_cross_version
a healthy non-draining, non-excluded backend exists
```

Defaults are:

| Setting | Default |
|---|---:|
| `policy.max_migrations` | 3 |
| `policy.max_migration_tokens` | 8192 |
| `policy.max_stream_duration` | 15m |
| `policy.allow_structured_resume` | false |
| `policy.allow_cross_version` | false |
| `policy.seam_window` | 64 bytes |
| `backend.quarantine_window` | 5s |
| `sse.max_event_bytes` | 1MiB |

`migrations_used` counts continuation attempts that were dispatched, including
an attempt that failed before producing a chunk. `elapsed` starts when `open`
is committed. The failed backend is excluded for at least the quarantine
window, and a draining backend remains excluded until administratively returned
to healthy service.

Template handling has a route setting `template_mode` with default `strict`:

| Verdict | `strict` | `permissive` |
|---|---|---|
| `SAFE` | eligible | eligible |
| `DEGRADED` | eligible with `template_degraded` warning | eligible with warning |
| `UNSAFE` | ineligible | eligible only after `template_unsafe_permissive` warning |
| unknown/not probed | ineligible | ineligible |

This preserves the safe default while implementing the conformance verdict
semantics. A backend admitted for ordinary serving may still be
migration-ineligible.

If any policy predicate fails, append one `warning` for each failed predicate
using its stable predicate name, then close with `error` code
`migration_refused`. If policy predicates pass but a correctness gate in
sections 11.4 or 11.5 fails, append its specific warning followed by the same
terminal error. The proxy never sends a fresh-generation request as a fallback.

### 11.3 Token accounting

`accumulated_tokens` and `tokens_already_emitted` use exact upstream incremental
usage or token IDs when available. OpenAI-compatible streams do not always
provide an exact mid-stream count. In that case Streamweld uses a conservative
model-aware counter when configured; otherwise it uses the UTF-8 byte count as
an upper bound for eligibility and remaining-token calculations and emits one
`token_count_estimated` warning. All affected event/state usage objects set
`estimated: true`. An estimate may refuse migration early but MUST NOT allow a
request past a configured token ceiling.

`rescued_tokens` is the completion-token count already accepted before a
migration. The telemetry series uses the same value and exposes estimated
accounting in structured logs so estimates are not presented as measured
tokenizer counts.

### 11.4 Request-shape correctness gates

#### Tool calls

The proxy incrementally tracks each chat `tool_calls` delta by choice and tool
index, including fragmented function-name and arguments JSON. A migration point
is inside a tool call from the first tool-call delta until the call has a
complete JSON argument value and the upstream choice declares the tool-call
boundary. If producer failure occurs in that interval, Streamweld appends
warning `tool_call_boundary` and terminal error `migration_refused`. It does
not concatenate, repair, or replay fragmented tool-call JSON.

#### Structured responses

`response_format.type` equal to `json_object` or `json_schema` is structured.
It is migration-ineligible unless `allow_structured_resume` is true. When
enabled, accumulated assistant bytes must be a valid JSON prefix: a streaming
parser must be in a state that can be extended by zero or more bytes into one
valid JSON value, with no invalid escape, literal, number, delimiter, or
trailing non-whitespace. The empty prefix is valid. An invalid prefix produces
warning `structured_prefix_invalid` and terminal error `migration_refused`.

Streaming requests with multiple simultaneous choices cannot be represented by
one assistant continuation in v1 and are handled as
`unsupported_continuation_shape`.

### 11.5 Continuation request

After eligibility succeeds, Streamweld:

1. freezes the accepted accumulated text and usage for the failed attempt;
2. selects a healthy target, excluding draining candidates and candidates whose
   quarantine window from a prior failure has not elapsed;
3. takes the normalized original request;
4. for chat, appends
   `{"role":"assistant","content":<accumulated_text>}` as the final message;
5. sets `continue_final_message: true` and
   `add_generation_prompt: false`;
6. preserves sampling parameters and an explicitly supplied `seed`;
7. sets the applicable `max_tokens` or `max_completion_tokens` to
   `max(1, original_limit - tokens_already_emitted)`; if no original limit was
   supplied, it remains absent;
8. forces streaming and dispatches to the selected target;
9. commits a `migration` entry before accepting any continuation chunk.

The original model name remains unchanged. Backend routing metadata is not
inserted into the model-visible conversation. An upstream continuation 5xx or
disconnect is another failure trigger and repeats eligibility with the updated
attempt count and exclusion set.

### 11.6 Seam reconciliation

The first continuation output is not journaled immediately. Streamweld buffers
complete SSE frames until it has at least `policy.seam_window` content bytes,
or until the attempt terminates if it produces fewer. If the boundary falls
inside a UTF-8 rune, buffering continues through that rune.

Let `held` be at most the configured leading window at UTF-8 boundaries.
Find the longest byte suffix of `accumulated_text`, also at UTF-8 boundaries,
that is a prefix of `held`. Strip that suffix from the leading continuation
content before serializing complete chunk frames. Record its byte length in
`streamweld_seam_overlap_bytes`. Empty rewritten chunks need not be journaled.

If overlap is zero, trim surrounding whitespace for inspection. When
accumulated text ends in a non-terminal character and continuation begins with
a Unicode uppercase letter, append warning `seam_anomaly` before the first
continuation chunk. Terminal characters are `.`, `!`, `?`, and the Unicode
ellipsis, optionally followed by closing quote or bracket characters.

Seam rewriting may alter only leading assistant text content. It MUST NOT alter
role, tool-call, usage, finish-reason, or other delta members. Every rewritten
event remains valid JSON when its upstream payload was JSON, and it is appended
only as a complete SSE frame. If safe rewriting is impossible, migration is
refused rather than emitting duplicate or malformed content.

## 12. Drain protocol

`POST /internal/backends/{addr}/drain` marks one backend draining. `addr` is
the percent-encoded canonical `host:port` registered in the backend pool. The
operation is idempotent.

The request may supply an optional `timeout` query parameter using a duration
such as `10s`; the default is `10s`. On acceptance the proxy atomically:

1. excludes the backend from new selection;
2. snapshots its bound in-flight streams;
3. triggers migration evaluation for every snapshot member with reason
   `drain`;
4. waits until its in-flight count reaches zero or the timeout expires.

It returns `200 OK` only at zero:

```json
{
  "backend": "10.0.0.12:8000",
  "state": "draining",
  "in_flight": 0
}
```

On timeout it returns `504 Gateway Timeout` with the same body and the remaining
`in_flight` count. The backend remains draining after either response. Streams
that are ineligible for migration follow the warning-plus-error rule, so their
producer attempts are canceled only after the terminal error is committed.
When a proxy has an admin token configured, both lower-level drain forms require
that token as `Authorization: Bearer ...`. This protects the low-level endpoint
on the shared proxy listener; the operator supplies the credential on its
downstream fan-out calls.

In a multi-replica operator deployment, a Pod drain MUST use the operator's
all-replica barrier instead of a load-balanced proxy Service:

```http
POST /internal/backends/by-pod/{namespace}/{pod}/drain HTTP/1.1
```

The operator discovers every non-terminating proxy EndpointSlice member,
including temporarily NotReady members which may still own streams, and sends
the same Pod drain to each replica directly. It returns `200 OK` only after
every discovered proxy acknowledges zero local in-flight streams:

```json
{
  "pod_namespace": "models",
  "pod_name": "vllm-0",
  "proxy_count": 2,
  "in_flight": 0,
  "state": "drained"
}
```

An empty proxy discovery result or any failed acknowledgement is fail-closed
with `503 Service Unavailable`. A completed fan-out with remaining streams is
`504 Gateway Timeout` and reports the aggregate `in_flight` count. Marks already
accepted by individual replicas remain draining, and retrying the barrier is
safe. The operator listener has no application bearer token because Kubernetes
HTTP lifecycle hooks cannot add one; it MUST remain isolated by namespace
NetworkPolicy and MUST NOT be publicly exposed.

Managed backend pods receive a `preStop` hook that calls the operator Service.
Manual `streamweldctl drain --namespace <namespace> <pod>` calls the identical
barrier. Deployments using this protocol can use
`terminationGracePeriodSeconds: 15`; the hook timeout must leave enough time
for HTTP completion and process exit.

Draining the proxy itself is distinct: readiness turns false, no new streams
are accepted, existing producer attempts are allowed to finish, and downstream
readers may reconnect to another Redis-backed replica. Backend migrations are
not initiated merely because a proxy is gracefully shutting down.

## 13. Remaining HTTP surface

| Method and path | Contract |
|---|---|
| `GET /v1/models` | Proxy the OpenAI-compatible model list from the healthy backend pool; no journal |
| `GET /healthz` | Process-liveness result; journal degradation alone does not make the process dead |
| `GET /readyz` | Ready only when the proxy can accept requests and at least one route/backend is serviceable |
| `GET /metrics` | Prometheus exposition, including the metrics in section 14 |

`/internal/*` is an administrative surface and SHOULD be bound or network
restricted separately from public inference endpoints. Protocol v1 does not
define end-user authentication, tenant isolation, billing, or RBAC.

### 13.1 Operator route snapshots

The operator programs every proxy replica without restarting it through:

```http
PUT /internal/routes/{percent-encoded-namespace/name}/backends HTTP/1.1
Authorization: Bearer <release-scoped-token>
Content-Type: application/json
```

The body is one bounded, strict JSON object containing `model`, the Kubernetes
object `uid`, `observed_generation`, `deleted`, the complete durability
`policy`, and the complete admitted `backends` set. Each backend carries its
immutable ID, HTTP origin URL, model version, template verdict, and Pod
identity. The response reports the applied generation, current serving backend
count, draining backend count, a bounded complete list of draining backend
identities when it fits, and active stream count. The operator requires the
serving count to agree, unions available draining identities (with a bounded
count fallback for mixed versions), and sums replica-local active streams.

Updates are atomic per proxy. A lower generation is rejected. An exact
same-generation retry is idempotent, while changed EndpointSlice content at
the same route generation replaces the snapshot. A different UID cannot take
over a live name. Deletion sends a UID- and generation-fenced empty tombstone
to every non-terminating proxy before the route finalizer is removed; only then
may a recreated object with a new UID claim the name. Backend records removed
from a snapshot stop receiving new leases immediately but remain accounted as
draining until their retained leases reach zero.

## 14. Observability contract

Metrics use `route` and `model` labels except where a metric has no meaningful
stream route. Implementations expose:

```text
streamweld_streams_active
streamweld_streams_total{outcome="done|stopped|error"}
streamweld_migrations_total{reason="crash|drain|stall|error_chunk|health"}
streamweld_migrations_refused_total{predicate="..."}
streamweld_tokens_rescued_total
streamweld_prompt_tokens_rebilled_total
streamweld_resumes_total{trigger="client|failover"}
streamweld_seam_overlap_bytes
streamweld_ttft_seconds
streamweld_inter_token_seconds
streamweld_stream_duration_seconds
streamweld_journal_bytes
streamweld_journal_degraded
streamweld_backends{state="healthy|draining|quarantined"}
```

Seam overlap, TTFT, inter-token time, and stream duration are histograms.
`streamweld_journal_degraded` is a 0/1 gauge. Every structured log line for a
stream includes `stream_id`. Logs use `log/slog` JSON output.

OpenTelemetry has one span per stream, one child span per backend attempt, and a
migration span event carrying reason, source, target, and rescued-token count.
Traces follow the applicable GenAI semantic conventions.

## 15. Journal degradation

Redis unavailability during `Open` produces the explicit degraded response
described in section 3.3 and the inference request proceeds without durability.
Redis unavailability after a stream opens follows these rules:

1. the current complete upstream event is still delivered to readers already
   attached to the producer owner's bounded local feed, including a remote
   reader with an already-established owner relay;
2. the producer is never canceled solely because journaling failed;
3. no uncommitted event receives a journal sequence;
4. the proxy emits an unsequenced, always-visible
   `streamweld.stream.warning` control event with code `journal_degraded` when
   possible;
5. the degraded gauge becomes 1 and a structured error is logged with the
   stream ID;
6. subsequent events for those attached connections pass through without
   claiming resumability.

If the journal later recovers, the proxy MUST NOT resume sequence allocation
after an unjournaled gap. That stream remains degraded until terminal transport
completion. A resume cursor at the committed boundary is rejected before
streaming with HTTP `410 stream_offset_expired`. When an earlier cursor permits
some committed entries to be replayed, the response has already begun with
HTTP 200 and its status cannot later change; after the committed prefix the
proxy therefore emits an unsequenced `streamweld.stream.error` carrying code
`stream_offset_expired` and closes. Clients MUST treat both representations as
the same terminal offset-expired outcome and MUST NOT present the prefix as a
complete result.

The unsequenced suffix and terminal outcome cannot be replayed after Redis
recovers. A new remote reader cannot discover the owner while Redis is
unavailable, and owner process loss destroys any suffix not committed to
Redis. These are explicit degraded-mode limits, not durable-delivery claims.

## 16. Configuration resolution

Effective values are resolved in this order:

1. built-in protocol defaults;
2. proxy-wide configuration;
3. the route's `DurabilityPolicy`;
4. an allowed per-request override (only orphan policy in protocol v1).

The durability policy has typed fields corresponding to:
`maxMigrations`, `maxMigrationTokens`, `maxStreamDuration`,
`orphanPolicy`, `orphanTimeout`, `allowCrossVersion`,
`allowStructuredResume`, `seamWindowBytes`, `journalTTL`, and
`templateMode`. Invalid combinations are rejected at configuration admission,
not coerced on the data path.

The principal defaults are:

| Configuration key | Default |
|---|---:|
| `journal.ttl` | 10m |
| `journal.backend` | `memory` (single replica) |
| `journal.max_bytes_per_stream` | 4MiB |
| `reader.max_lag_bytes` | 1MiB |
| `reader.write_timeout` | 30s |
| `policy.max_migrations` | 3 |
| `policy.max_migration_tokens` | 8192 |
| `policy.max_stream_duration` | 15m |
| `policy.orphan_policy` | `continue` |
| `policy.orphan_timeout` | 60s |
| `policy.allow_cross_version` | false |
| `policy.allow_structured_resume` | false |
| `policy.seam_window` | 64 bytes |
| `policy.template_mode` | `strict` |
| `migration.stall_timeout` | 30s, detector disabled |
| `backend.quarantine_window` | 5s |
| `relay.advertise_url` | unset (relay disabled) |
| `relay.heartbeat_interval` | 2s |
| `relay.presence_ttl` | 10s |

`journal.max_total_bytes`, `reader.max_lag_bytes`, and
`reader.write_timeout` MUST be positive. The
standalone proxy defaults them to `256MiB` and `1MiB`; deployment manifests
render both values explicitly.

## 17. Conformance checklist

An implementation conforms to this protocol only if automated tests demonstrate:

- lowercase ULID identity in both response header and first `open` event;
- atomic idempotent replay without a second upstream generation;
- exact-once replay from an exclusive `Last-Event-ID` cursor;
- replay-to-tail behavior under a concurrent append;
- multiple independent readers from sequence zero;
- distinct done, stopped, error, disconnect, expired, and never-seen outcomes;
- terminal append rejection;
- explicit stop cancellation and non-resumability;
- all three orphan policies, including attach/timer races;
- every migration trigger and every refusal predicate;
- migration entry ordering before continuation chunks;
- UTF-8 splits across reads, multi-line SSE data, comments, retry fields, and
  incomplete EOF;
- seam overlaps of zero, partial-window, full-window, and multibyte text;
- refusal during fragmented tool-call JSON;
- structured JSON valid-prefix acceptance and rejection;
- slow-reader eviction without producer backpressure;
- memory retention gaps reported rather than hidden;
- Redis loss before open and during append degrading without dropping the
  inference request;
- cross-replica replay with Redis and rejection of multi-replica memory mode;
- an already-established owner relay carrying the degraded suffix to a remote
  reader, with mutual-TLS and metadata/header privacy gates;
- drain exclusion, proactive migration, timeout, and idempotency.

These tests use deterministic expected output. Performance or resilience claims
must come from committed reproducible benchmark results, not from this protocol
document.
